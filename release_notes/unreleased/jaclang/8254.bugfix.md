- **Fix: a warm module cache no longer changes a checker verdict on distinct types** (issue #8239): the same source checked clean on a cold cache and reported `E1053: Cannot assign int to parameter 'object' of type Branded` on a warm one, for `out: list[Branded]` fed a raw `int` through `out.append(k)`. Nothing about the brand itself differed between the runs -- `distinct_key` and the shared class details were identical -- what differed was the module's placement, and behind it a memoized environment probe. `native_pipeline_available` asked `get_inference_sched()` whether type inference existed and read an empty schedule as "vendor/typeshed stubs are not available in this environment", but a schedule is also empty while the checker passes are mid-import: a warm cache changes the order the compiler's own modules load, and one probe landed while `jaclang.compiler.symbol_utils` was partially initialized, so a transient `ImportError` became a permanent, mislabeled environment fact and native placement was refused for every module in that process. Placement then reached the checker, because `assign_type`'s native pointer/int relaxation answers before `_assign_class` runs its brand check, so the native lane accepted the raw `int` and the server lane rejected it. The probe now tests the vendored stub path on disk -- the same test `get_inference_sched` already made, shared as `typeshed_stubs_available` -- so the verdict is a function of the filesystem rather than of what happened to be importable at that instant, and the shim probe now separates a package that is genuinely absent (`ModuleNotFoundError`, still recorded as a missing shim) from one that is only mid-import, which answers "undecided" without memoizing so the next probe can decide.
- **Fix: an erased distinct type is enforced in every codespace**: a check-time brand is erased by jac0, sv and native alike, so the verdict cannot follow placement. Two native relaxations in `assign_type` treated any int-shaped source and destination as mutually assignable and answered before the brand check, which silently accepted a raw base value where a branded one was declared in a natively-placed module. Both now go through one `_distinct_brand_mismatch`, the same predicate `_assign_class` uses, and do not fire when the destination carries a brand the source does not share.
- **Fix: a warm module cache no longer degrades a module's codespace** (issue #8257): on a warm cache every client-codespace probe raised `ImportError: cannot import name 'collect_assigned_symbols' from partially initialized module 'jaclang.compiler.symbol_utils'` and each module quietly became a server module (cold 0 failures, warm 37, deterministic). Three faults compounded. **The cache key was not a function of the module**: `_project_env_fingerprint` folded in `_module_codespace_mode`, which reads the *ambient* default codespace -- the ContextVar that whatever compile scope is in flight sets and restores -- so a compiler-source entry written under one scope was rejected under another with its source unchanged. The ambient codespace cannot reach such a module in the first place, since `parse_str` never runs placement inference for the internal program, so compiler-source modules now key as `internal` while a user module keeps the ambient value that does decide its placement. **A live import could trigger a full compile of the module being imported**: the rejected entry sent `get_bytecode` into a fresh compile inside `exec_module`, and the full pipeline imports names from `jaclang.compiler.symbol_utils` at pass-run time (`CFGBuildPass` for `collect_assigned_symbols`, `EsastGenPass` for `report_client_bare_import_uses`), so compiling `symbol_utils.jac` re-entered a half-initialized `symbol_utils`. That is the hazard the schedule-loading window already guards, and it now takes the same answer: a compile whose module Python is currently importing uses the bootstrap IR schedule and the minimal `PyastGenPass` + `PyBytecodeGenPass` codegen, scoped to the internal program so no user module's placement or client codegen changes. **The degradation was silent**: `module_is_client` answered "server" for any probe failure, so a compiler-source `ImportError` read as a codespace verdict. A failure whose origin is the compiler's own source now raises `CompilerSourceError` naming the probed file and the offending module instead of answering, while a failure in the probed source keeps the note and the server fallback.
